# Queued message delivery mode

Queued tasks default to `delivery_mode: wait`; persisted tasks without this field retain existing behavior. For an existing local or SSH thread, `steer` attempts delivery to the current active turn after the configured queue-entry time. If no active turn exists, normal scheduling, concurrency limits, quota checks and interrupted-task recovery still apply. Steering an existing turn does not consume a new concurrency slot and may bypass messages waiting for completion.

The existing Codex control WebSocket must belong to the process running the target turn. A separate CLI `exec resume` process cannot steer that turn. The helper initializes the connection, reads live turns through `thread/read` with `includeTurns`, then invokes `turn/steer` with `expectedTurnId`. It sends only the prompt: the active turn's model, project and other settings remain unchanged. SSH uses the selected server's configured Codex home.

Reference: https://learn.chatgpt.com/docs/app-server#steer-an-active-turn

A successful acknowledgement is recorded as `steered` (input accepted by the active turn), including `assigned_turn_id`. Acceptance can precede consumption and persistence of the message. The helper sends a fresh `clientUserMessageId` for desktop correlation, then reads history for up to six seconds to confirm a new `userMessage` in that same turn. It stores the confirmed item ID as `steer_message_id`. Older servers without client IDs are matched by exact text and an item ID absent from the pre-send snapshot. Existing identical messages and messages in another turn do not count as confirmation.

The UI distinguishes accepted input with unconfirmed recording from a confirmed history item. If confirmation times out or history cannot be read, the accepted request is never resent or reported as rejected. Old saved `steered` records remain accepted with unconfirmed recording. A confirmed history item does not guarantee the desktop has refreshed its transcript; the UI suggests reopening the chat if the message is missing. This is deliberately distinct from `completed`: it does not assert that the active turn has finished. Missing control sockets, unsupported APIs, turn-ID races, and uncertain transport outcomes are shown as errors. No CLI fallback or automatic resend follows a steer attempt, since a lost response may hide successful delivery. Inspect the target thread before manually retrying an uncertain result.

Durable rule: never turn a steer acknowledgement into turn completion, never apply model/cwd overrides to `turn/steer`, and never silently replace a failed/uncertain steer with `turn/start` or CLI execution. Re-read live turn state rather than trusting a potentially stale history snapshot.

Regression coverage: `python3 scripts/test_codex_queue_steering.py` exercises the shipped helper against a deterministic WebSocket peer, including delayed recording, legacy servers, acknowledgement-only delivery, disconnects, repeated text, other turns, client-ID mismatches, and rejected/mismatched acknowledgements.

For the reported October 30 incident, read-only inspection of the remote rollout confirmed the exact prompt and its completed `UserMessage` event at 03:57:36 Asia/Shanghai, about three seconds after acknowledgement. The message was delivered; its absence in the desktop transcript was not evidence of failed steering. No production message was resent during diagnosis.
